# Recommendation event collection

## Purpose and lawful basis

Seasonly uses a separate, optional personalization consent before storing identifiable
recommendation interactions. This is deliberately separate from allergy-storage consent because
interaction history may be combined with, or used to infer, health-related preferences. Inferred
health data can become special-category data when it is used to profile or treat a person
differently (Information Commissioner's Office, 2026a).

Core functionality does not depend on personalization consent. Favourites, recipe history and
planned meals remain available when consent is refused or withdrawn. They are not training inputs;
the recommendation pipeline must read only from the consent-gated `recommendation_events` table.

For the current private pilot, consented events may personalize only that tester's live feed. The
brief sessions are excluded from prototype training, tuning and effectiveness evaluation. The
offline ML pipeline continues to accept only datasets explicitly classified as synthetic; see
`docs/private-pilot-and-synthetic-ml.md`.

## Data collected

The event table contains only:

- a random event identifier;
- the authenticated user, recipe and authorising consent identifiers;
- a random slate identifier shared by impressions displayed in the same feed request;
- a constrained event type and source;
- an optional feed position;
- server-controlled occurrence and expiry timestamps.

No allergy value, recipe description, device identifier, advertising identifier, IP address or
free-form metadata is copied into an event. Current event types are impressions, opens, favourites,
unfavourites, plans and unplans. State-changing events are generated by the backend only.
The recommendation feed endpoint issues one random `slate_id` for each ranked response. When
personalization consent is active, the iOS client reuses that server-issued identifier and submits
displayed impressions in a batch with idempotent event UUIDs. Filtered seasonal browsing is not
logged as recommendation exposure. The slate identifier is operational metadata rather than
free-form tracking data: it is required to reconstruct the candidate group for offline ranking
evaluation and to snapshot history before all candidates in that group.

## Consent lifecycle

The current consent notice version is `2026-07-24`.

- Without active consent for the current notice version, action-event recording is a no-op and
  impression submission is rejected.
- Granting consent creates a versioned consent record.
- A new notice version requires new consent.
- Withdrawal timestamps active personalization consents and deletes all identifiable
  recommendation events for that user in the same transaction.
- Withdrawal does not delete favourites, history or planned meals.

## Retention

Each identifiable event expires 365 days after collection. The
`recommendation-maintenance` Docker service removes expired rows daily. A one-off purge can also be
run with:

```bash
./scripts/uv run python backend/scripts/purge_expired_recommendation_events.py
```

UK GDPR does not prescribe a universal number of days, but it requires a justified retention
period, periodic review, and erasure or anonymisation when identifiable data is no longer needed
(Information Commissioner's Office, 2026b). Seasonly therefore stores no identifiable event beyond
12 months. Future aggregate statistics may survive only after a separate process verifies that
they are genuinely anonymous; this section does not create such aggregates.
